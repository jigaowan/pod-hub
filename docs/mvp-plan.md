# Pod Hub MVP Plan

## 项目目标

Pod Hub 是一个自托管的 YouTube-to-Podcast 工具，用于将指定 YouTube 频道的公开节目转换为可订阅的 Podcast feed，并对外提供稳定的音频访问链接。

## MVP 范围

当前首版范围固定如下：

- 管理员手动录入 YouTube 频道，输入形式可以是频道 URL、`@handle` 或频道 ID。
- 系统为每个频道建立一个订阅源，并维护稳定的公开 feed 链接。
- 系统按固定周期轮询频道更新，首次接入时获取频道的全部视频列表并写入数据库，但仅抓取最近 `N` 期节目的音频；后续每轮同步也使用同一个 `N` 作为旧节目补抓批次上限。
- 节目发现与元数据提取使用 `yt-dlp`，音频下载与提取也使用 `yt-dlp`。
- 音频文件由系统本地托管，并在 feed 中作为 `enclosure` 对外暴露。
- 系统提供简单 Web 后台，用于录入频道、查看同步状态和查看节目处理结果；同步仅由定时调度触发。
- 项目以 Docker 方式交付，默认部署形态为单容器、单应用。

## 非目标

以下内容明确不在首版范围内：

- 不做多用户与权限系统。
- 不做 feed 鉴权、私有链接或账号登录。
- 不做 AI 摘要、转写、内容增强或音频编辑。
- 不保证私有视频、会员视频、区域限制视频或需要 cookies 的内容可处理。
- 不以公开 SaaS 服务为目标，首版仅面向自托管使用场景。
- 不引入独立消息队列、独立 worker 集群或复杂分布式架构。

## 核心流程

首版端到端流程固定如下：

1. 管理员在后台录入 YouTube 频道标识。
2. 系统使用 `yt-dlp` 对频道进行列表提取，只枚举节目，不在扫描阶段下载媒体。
3. 首次接入时，系统获取该频道的全部视频列表并为每个视频建立节目记录。
4. 系统优先对最近 `N` 期节目执行元数据提取、音频下载与转码，生成可供播客客户端使用的音频文件。
5. 后续轮询时，系统先识别并抓取新节目，再顺带抓取最多 `N` 个尚未抓取音频的旧节目，逐步补齐历史库存。
6. 系统将节目元数据、处理状态和本地媒体路径写入数据库。
7. 系统仅将已完成本地音频抓取的节目写入频道 RSS feed。
8. 播客客户端通过公开 feed URL 订阅，并通过系统提供的媒体 URL 拉取音频。

## 技术约束

当前已确认的实现约束如下：

- 后端技术栈使用 `Python`。
- Web 框架采用 `FastAPI`，管理界面采用服务端渲染模板。
- 数据持久化使用 `SQLite`。
- 应用以单体方式提供 Web、调度、feed 输出和后台任务能力。
- 进程内调度采用单进程串行任务模型，不引入显式任务队列系统。
- 默认部署方式为单容器 Docker 应用，并通过挂载卷持久化数据库和媒体文件。
- 管理界面为简单 Web 后台，不优先提供 CLI-only 或复杂前端后台。

## YouTube 抓取决策

### 当前结论

节目发现和音频下载统一使用 `yt-dlp`，不依赖 YouTube Data API。

### 决策理由

- 首版目标是自托管 MVP，优先减少部署前置条件，不要求配置 Google API key。
- 发现与下载使用同一套工具，链路更短，运维复杂度更低。
- 对于公开频道的节目枚举和下载，`yt-dlp` 已具备成熟的提取能力，足以支撑 MVP。
- 当前重点是尽快验证“频道转 Podcast feed”的闭环，而不是优先构建官方 API 集成能力。

### 强制约束

- 节目发现和音频下载都使用 `yt-dlp`。
- 频道扫描阶段只做列表提取，不直接下载媒体。
- 首次接入必须记录频道的全部视频列表，但只抓取最近 `N` 期节目的音频。
- 后续定时轮询时，除抓取新节目外，还要使用同一个 `N` 补抓最多 `N` 个未抓取的旧节目。
- 首版只支持公开视频。
- feed 只暴露已完成本地音频抓取的节目，不向播放器暴露缺失 `enclosure` 的占位条目。
- `yt-dlp` 版本必须在镜像中固定，不使用不受控的 `latest`。

### 已知代价与风险

- 系统稳定性依赖 `yt-dlp` 对 YouTube 页面结构变化的适配能力。
- 当 YouTube 改动页面或反爬策略时，可能需要升级 `yt-dlp` 才能恢复可用性。
- 通过下载并重新分发音频提供 Podcast 订阅，存在平台条款与版权合规风险。
- 不接入官方 API 意味着元数据可控性、稳定性和长期兼容性弱于官方方案。

## 数据与公开接口

### 最小稳定数据模型

系统至少需要稳定保存以下信息：

- 频道：
  - `channel_id`
  - `source_url`
  - `source_kind`
  - `display_name`
  - `slug`
  - `status`
  - `last_synced_at`
  - `last_error`
- 节目：
  - `video_id`
  - `channel_id`
  - `webpage_url`
  - `title`
  - `description`
  - `upload_date`
  - `duration`
  - `thumbnail`
  - `audio_path`
  - `status`
  - `audio_fetched_at`
  - `listed_at`
  - `last_error`
- 同步任务：
  - `run_id`
  - `channel_id`
  - `status`
  - `started_at`
  - `finished_at`
  - `discovered_count`
  - `fetched_count`
  - `failed_count`
- 应用设置：
  - `key`
  - `value`
  - `updated_at`

### 最小稳定公开接口

首版需要提供稳定的公开资源路径：

- RSS feed：`/feeds/{channel_slug}.xml`
- 音频文件：`/media/{episode_id}.m4a`
- 管理后台：HTTP 页面，至少可完成频道录入、频道列表查看、频道详情与同步状态查看

以上路径可在实现时调整细节，但语义必须保持稳定：每个频道都有固定 feed，每期节目都有固定音频访问 URL。

## 运行配置

首版至少应支持以下配置项：

- `BASE_URL`：系统对外公开访问的基地址，用于生成 feed 与媒体绝对链接。
- `FETCH_BATCH_SIZE`：统一控制每个频道单轮抓取上限；首次接入抓最近节目，定时轮询时优先抓新节目，剩余额度再补历史节目。
- `SYNC_INTERVAL`：定时轮询频道更新的周期。
- `MEDIA_DIR`：音频文件存储目录。
- `DATABASE_PATH`：SQLite 数据库文件路径。
- `LOG_LEVEL`：基础日志输出级别。

所有配置均应适配 Docker 环境，并允许通过环境变量注入。

## 验收标准

首版成功的判断标准如下：

- 管理员接入一个公开 YouTube 频道后，系统能够生成对应的 Podcast feed。
- 常见播客客户端能够识别该 feed 为有效 RSS 并完成订阅。
- 首次同步能够记录该频道的全部视频列表，同时只抓取最近 `N` 期节目的音频。
- 新节目发布后，系统能够在一个轮询周期内将其加入 feed。
- 在持续轮询过程中，系统会逐步补抓尚未抓取的旧节目，而不会无限停留在“只抓新视频”状态。
- feed 中只包含已有可访问音频文件的节目，且每期节目的音频链接可播放、可持续复用。
- 应用重启后，数据库状态和已下载媒体文件不会丢失。
- 后台能够明确展示处理成功、处理中、失败三类状态，并展示最近一次调度结果与错误信息。

## 决策记录

以下为当前已确认的关键决策与理由：

| 决策项 | 当前结论 | 理由 |
| --- | --- | --- |
| 产品定位 | 自托管工具 | 优先满足个人或小团队部署，不按公开 SaaS 设计 |
| 来源录入方式 | 管理员手动录入频道 | 首版流程最短，避免用户侧权限与滥用治理 |
| 订阅可见性 | 公开可访问 feed 链接 | MVP 实现成本最低，便于直接验证播放器兼容性 |
| 首次回填策略 | 全量记录视频列表，仅抓取最近 `N` 期音频 | 兼顾完整目录感知与首轮同步成本控制 |
| 更新机制 | 定时轮询 | 足以满足首版时效目标，复杂度低于实时方案 |
| 历史补抓策略 | 每轮同步补抓最多 `N` 个未抓取旧节目 | 用统一批量参数减少配置复杂度，同时逐步补齐历史库存 |
| 音频策略 | 下载并本地托管 | 能提供稳定 enclosure，避免依赖上游资源 |
| Feed 暴露策略 | 仅发布已抓到本地音频的节目 | 避免播放器看到无效条目或缺失 enclosure |
| 管理入口 | 简单 Web 后台（仅新增和查看） | 比配置文件更直观，同时避免首版引入编辑、删除和手动运维动作 |
| 数据存储 | `SQLite` | 适合自托管 MVP，部署成本低 |
| Python 栈 | `FastAPI` + 服务端渲染 | 单体结构清晰，足以承载后台页面与公开路由 |
| 处理模型 | 单进程串行后台任务 | 控制资源占用，避免 SQLite 写竞争与重复抓取 |
| 部署形态 | Docker 单容器单应用 | 默认交付最简单，便于落地 |
| YouTube 抓取方式 | `yt-dlp-only` | 避免 Google API 依赖，统一发现与下载链路 |
| 扩展方向 | 数据模型预留 playlist | 首版只做频道，但避免后续推翻模型 |
